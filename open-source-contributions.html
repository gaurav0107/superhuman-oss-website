superhuman/Contribution guide

Contribute to open source with an AI agent, carefully.

AI-written pull requests are a sore point in open source, because a maintainer's review time is the scarce resource. This guide is what we learned from the pull requests maintainers merged, and how superhuman puts it into practice for Claude Code and Codex.

What maintainers merge

These patterns run through the merged pull requests on the Merge Wall:

  • Small and scoped. One issue, one change. No drive-by refactors.
  • The issue is real and open. Nobody else has claimed it and there is no competing pull request.
  • It looks like the project wrote it. Same commit format, PR template, test style and lint rules as the last merged pull requests.
  • Tests where the project expects them. And the project's own CI passes before anyone is asked to look.
  • A clear, honest description. What changed, why, how it was tested, and that an agent helped.
  • Review gets answered. Quickly, and by fixing what was asked rather than arguing.

Picking issues

Most wasted effort starts with the wrong issue. superhuman's issue-selector skips issues someone has already taken, issues with a competing pull request, issues marked docs-only and issues opened less than a day ago. Its repo-finder prefers projects whose maintainers respond and that already review outside contributions. You can steer both with /preferences, or aim at one issue directly with /contribute owner/repo 12345.

Matching the house style

Before it writes a line, repo-profiler reads the project's last 10–20 merged pull requests and its CI workflows: commit format, branch names, PR template, test runner, lint commands, what reviewers ask for. Those become the conventions the change is held to, and the CI commands it is allowed to run.

A workflow with superhuman

  1. Install with one command, then restart Claude Code. See the plugin, commands and skill.
  2. Say what you like with /preferences: languages, topics, a star floor.
  3. Build a shortlist with /repo-finder.
  4. Contribute with /contribute. It forks the project, plans, builds test first, opens a draft pull request and improves it until its own score says it is ready for review.
  5. Come back later with /contribution-sweep, which lists the pull requests waiting on you: changes requested, a merge conflict, failing CI.

Disclosure and responsibility

The pull request opens from your fork, under your name, and you are responsible for it like any other change you send. By default its body says it was opened with superhuman, so the maintainer knows what they are reviewing. Commits stay authored by you, with no AI co-author trailers.

What superhuman does not do: push to the upstream repository, run commands outside the allowlist, or answer reviews after its run has ended. Those are yours.

Questions

Is it OK to use AI to contribute to open source?

Many projects accept AI-assisted contributions when they are small, correct, tested and disclosed; some do not. Read the project's CONTRIBUTING file first, and respect a project that says no.

What makes an AI pull request get merged?

The same things that get any pull request merged: a real open issue, a small scoped change, the project's conventions, passing CI and a clear description. Answering review quickly matters as much as the code.

Will the pull requests be under my name?

Yes. superhuman runs under your GitHub account; the pull request opens from your fork and the commits are authored by you.

Where can I see real examples?

Every pull request opened with superhuman and merged by maintainers is on the Merge Wall, each with a link to the real review.
