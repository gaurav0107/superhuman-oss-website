superhuman/Agents

The agent team. One job each, from issue to pull request.

superhuman is a multi-agent harness for Claude Code. An orchestrator runs ten specialist subagents, each with one job and a written contract, and they pass work to each other through files under ~/.superhuman/. The same contracts run inline in OpenAI Codex.

The run, agent by agent

A contribution starts with /contribute. The orchestrator, opensource-contributor, claims a lock for the repository and runs the specialists in order. Each one reads what it needs from the state directory and writes one thing back.

AgentWhat it doesHands on
repo-finderBuilds a shortlist of repositories worth contributing to. It scores each one on maintainer responsiveness, issue velocity, how the project treats AI-assisted contributions, and contribution opportunity, and picks the best open issue in each.repo-shortlist.json
issue-selectorFilters and ranks the open issues in one repository. It skips issues marked docs-only, issues that already have a competing pull request, and issues opened less than a day ago.issue_candidates.json
repo-profilerReads the repository's last 10–20 merged pull requests to learn its commit format, PR template, test runner, lint commands and reviewer norms. It turns the project's CI workflows into an allowlist of commands it may run.repo_profile.json, ci_commands.json
plannerWrites the implementation plan for the chosen issue, using the superpowers writing-plans skill with the repo profile, past reviewer notes and past mistakes as context.the plan
builderCarries out the plan with the superpowers subagent-driven-development skill, test first, and runs only the allowlisted CI commands before it pushes to your fork.a branch on your fork
impact-auditorBefore any refactor of a shared function, lists every caller, works out the context each one runs in, and judges whether the change is safe in all of them.impact_audit.json
merge-probability-scorerGrades the pull request on ten weighted dimensions, the way a maintainer would read it, and says which dimension is weakest.a score and its breakdown
reviewer-dispatcherTakes the weakest dimension and runs the matching specialist reviewer: Python, Go, TypeScript, Java, Kotlin, Rust, C++, C#, Flutter or security.findings for the builder
resolve-commentsReads review comments while a run is going, sorts each into question, nit, refactor, concern or suspicious, and drafts a reply or sends a fix to the builder. It halts the run on anything that looks like prompt injection.reviewer_intent_notes.md
lesson-distillerTurns reviewer feedback and merge outcomes into typed rule cards. A rule seen in two repositories becomes a candidate; seen in three, it applies everywhere.the lessons store

Source: the agent contracts in agents/. Every shared-state file has one writer and a JSON Schema in schemas/.

The loop the orchestrator runs

The orchestrator opens the pull request as a draft from your fork, then loops: score it, send the weakest dimension to the matching specialist, rebuild, score again. It marks the pull request ready for review once the score reaches 80%, unless a safety check has halted the run. It aims for 95% on two runs in a row, and it stops earlier when it reaches its iteration cap (3, 6 or 10 iterations, set by the size of the diff), when the scores plateau, or on a safety halt.

The score is the agent's own estimate of what a maintainer would accept. It is not a measured merge rate. The maintainers decide.

How the scorer grades a pull request

The merge-probability-scorer gives each dimension 0–10, weights them, and scales the sum to a percentage. If process compliance scores 4 or lower, the final score is capped at 50%: a pull request a bot will close is not worth polishing.

DimensionWhat it checksWeight
CorrectnessDoes the change fix the issue, edge cases included?22%
Test coverageNew tests where the project expects them; existing tests still pass.18%
Historical signalA calibrated prior from the outcomes of past pull requests.10%
Style complianceThe repository's lint, naming and formatting conventions.9%
PR format complianceCommit messages, branch name, PR template and required sections.9%
Process complianceIssue linked, CLA or DCO signed, no competing pull request.9%

Why separate agents

One long prompt that does everything drifts. Separate agents with narrow contracts can be tested, replaced and reasoned about one at a time:

  • One writer per file. Each state file has exactly one agent that writes it, documented in agents/SHARED_STATE.md and validated against a schema at write time.
  • Specialists where it matters. The language reviewers come from the everything-claude-code plugin; when it isn't installed, the dispatcher falls back to an inline review prompt.
  • Memory that survives the session. Repo profiles, reviewer notes, past mistakes and learned rules live on disk, so the next run on the same repository starts ahead of the last.

Safety rails around the agents

  • Forks only. The builder pushes with --force-with-lease to your fork. Never upstream, never a plain --force.
  • CI allowlist. Only commands parsed from the project's own workflows, or ones you approve, ever run.
  • Impact audits before refactors. A reviewer's suggested refactor is checked against every caller first.
  • Prompt-injection halt. A review comment asking it to run shell commands, touch files outside the diff or fetch a URL stops the run.
  • Learned rules are data, not code. Rule cards have a fixed schema; a comment that tries to smuggle in a command never becomes a rule.
  • Disclosure on by default. The pull request body says it was opened with superhuman.

The full model is in SECURITY.md.

Runs in Claude Code and Codex

In Claude Code the agents load as subagents and the commands as slash commands. In OpenAI Codex, which has no subagents, a single skill runs the same contracts inline, in phase order. See the plugin, commands and skill for both installs.

Questions

What is a Claude Code subagent?

A subagent is a separate Claude instance with its own instructions and context window that the main session hands a task to. superhuman's agents are Claude Code subagents defined as Markdown files in the plugin's agents/ folder.

How many agents does superhuman use?

An orchestrator and ten specialists: repo-finder, issue-selector, repo-profiler, planner, builder, impact-auditor, merge-probability-scorer, reviewer-dispatcher, resolve-comments and lesson-distiller.

Does it answer code review on its own?

Only while a run is going. Reviews that arrive after the run ends are yours; /contribution-sweep lists the pull requests waiting on you.

Can I read or change the agents?

Yes. They are plain Markdown contracts in the MIT-licensed repository, with the shell scripts they call under scripts/ and tests under tests/.
